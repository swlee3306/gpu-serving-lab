# Step 1c — 이 서버(RTX 4070 Ti SUPER 16GB)에서 최적 설정 찾기

## 목표와 판정 규칙
- 품질: 정답이 있는 객관식 200문제 정확도 (KMMLU 컴퓨터과학 100 + MMLU machine_learning 100, temperature 0). 같은 서버에서 2번 돌려 대조군(흔들림)을 잰다. 표본이 작아 ±3~4%p 차이는 우연일 수 있다.
- 속도: 현실적 부하(`bench_real.py`, 포아송 도착, 제각각 프롬프트)에서 SLO(TTFT p95 ≤ 300 ms, 1인 ≥ 30 tok/s)를 지키는 최대 도착률.
- 한 번에 한 가지만 바꾼다. 1차는 모델·KV 종류, 2차는 서버 설정(조사에서 나온 후보).
- 주의: 도착률마다 요청 구성이 달라(seed), SLO 경계 근처(예: 4/s)에서는 통과/실패가 흔들릴 수 있다. 표의 TTFT p95 값을 함께 본다.

## 조사 결과 (ego-browser로 읽음, 2026-11-02)
- vLLM 최적화 문서: `max_num_batched_tokens` 작으면 ITL↑, 크면 TTFT↑, 처리량엔 >8192 권장 / 선점 잦으면 util↑ 또는 `max_num_seqs`↓.
  https://docs.vllm.ai/en/latest/configuration/optimization/
- 양자화 KV 문서: 기본 fp8은 보정 없음(scale 1.0), 보정은 llm-compressor 권장.
  https://docs.vllm.ai/en/latest/features/quantization/quantized_kvcache/
- vLLM 블로그(2026-04-22): fp8 KV는 Hopper/Blackwell에서 검증. 짧은 컨텍스트(<7k)는 BF16이 ITL 약간 유리할 수 있음. 정확도 95% 미만이면 BF16 또는 보정.
  https://vllm.ai/blog/2026-04-22-fp8-kvcache
- Red Hat 가이드(2026-03): util 0.95까지 점진 상승, `max_num_seqs`를 포화 지점으로 제한, fp8 KV는 자동 평가와 함께, 대표 데이터셋 사용.
  https://developers.redhat.com/articles/2026/03/03/practical-strategies-vllm-performance-tuning
- 읽지 않음: AWQ vs GPTQ 비교 글들(제목만 확인).
- 적용 시 주의: 위 글은 주로 H100급 기준. 우리 GPU(Ada)와 모델(3B/7B)에서는 직접 측정으로만 확인한다.

## 결과
### 1차 결과 (util 0.85, max-model-len 8192)
| 후보 | KV 총칸 | 정확도 ko/en/전체 (2회) | 파싱실패 | 대조군(답 달라진 문제) | SLO 통과 도착률 | TTFT p95 (4/s) | 최대 KV 사용률 |
|---|---|---|---|---|---|---|---|
| A 3B fp16 KV | 177,120 | 59/48/53.5, 59/47/53.0 | 7 | 1/200 | 2, 6, 8 (4는 313ms로 경계 실패) | 313 ms | 21% |
| B 3B fp8 KV | 332,640 | 50/42/46.0, 48/40/44.0 | 23~27 | 13/200 | 2, 4, 6, 8 | 279 ms | 19.5% |
| C 7B AWQ fp16 KV | 115,184 | 67/46/56.5, 67/46/56.5 | 0 | 0/200 | 2만 (4/s에서 850ms) | 850 ms | 16.5% |
| D 7B AWQ fp8 KV | 218,000 | 37/29/33.0, 37/30/33.5 | 12 | 7/200 | 2만 | 761 ms | 7.9% |

### 1차에서 읽은 것
1. **보정 없는 fp8 KV는 이 환경에서 품질을 떨어뜨렸다.** 3B는 53.5→45 (−8.5%p), 7B는 56.5→33 (−23%p). 파싱 실패(형식 깨짐)도 늘었고, fp8 서버는 같은 질문에도 답이 흔들렸다(13/200, 7/200). 표본이 200문제라 ±3.5%p 정도는 우연일 수 있지만, 이 차이는 그보다 크다. (Ada GPU, 보정 없음이라는 조건에서만 확인. 보정하면 달라질 수 있음 — 미측정.)
2. **fp8의 속도 이득은 SLO 구간에서 보이지 않았다.** 3B A→B의 TTFT p95는 2~8건/초에서 거의 같다(차이가 흔들림 범위). SLO 한계 근처(10건/초)에서도 KV 사용률은 약 20%라 KV가 병목이 아니다. KV가 가득 차는 건 20건/초 이상의 과부하 구간뿐이고, fp8이 도움이 된 것도 거기였다.
3. **7B AWQ는 3B보다 TTFT가 훨씬 느리다.** 4건/초에서 p95 850 ms vs 313 ms. 3B가 SLO를 지키는 8건/초 근처에서 7B는 2건/초 근처가 한계. 품질은 한국어 +8%p(67 vs 59)이지만 영어는 −2%p, 전체 +3%p로 표본 오차 범위 안이다.
4. 따라서 2차에서는 **util(KV 늘리기)과 fp8을 후보에서 뺀다.** 근거: SLO 구간에서 KV가 병목이 아니다. 대신 TTFT를 지배하는 prefill 스케줄링(`max-num-batched-tokens`)과 동시 상한(`max-num-seqs`)을 시험한다.

### 2차 결과 (3B, fp16 KV, util 0.85)
| 후보 | KV 총칸 | 정확도 전체 | TTFT p95 @6 / @8 / @10 / @12 | SLO 통과 |
|---|---|---|---|---|
| A (1차) | 177,120 | 53.5 / 53.0 | 247 / 282 / 480 / - | 6, 8 |
| A2 (재측정) | 177,120 | 53.5 / 53.0 | 248 / 278 / 473 / 1226 | 6, 8 |
| E mbt 2048 | 177,120 | 53.5 / 53.0 | 248 / 277 / 475 / 1220 | 6, 8 |
| F mbt 16384 | 158,976 | 53.5 / 53.0 | 260 / 316 / 485 / - | 6만 (8에서 316ms 실패) |
| G seqs 64 | 187,536 | 52.5 / 52.5 | 248 / 281 / 779 / 3268 | 6, 8 |

### 2차에서 읽은 것
1. **측정은 재현된다.** A와 A2는 같은 요청 구성(seed)에서 TTFT p95가 ±5 ms 안에서 일치했다. 1차에서 A의 4건/초가 313 ms로 실패한 것은 "측정 흔들림"이 아니라 그 도착률의 요청 구성(100개 표본)이 주는 값이다. 즉 SLO 통과 여부는 요청 구성에 따라 경계에서 갈릴 수 있다.
2. **`max-num-batched-tokens` 2048은 기본값과 완전히 같은 결과**(KV 칸 수 177,120까지 동일). 그래서 이 GPU의 기본값이 2048일 가능성이 높다(추정, 설정값을 직접 읽지는 않음). 16384로 키우면 오히려 TTFT가 나빠지고(@8 316 ms) KV 예산이 줄었다(6.08→5.46 GiB, 실행 중 버퍼가 커짐). 공식 문서의 "8192 초과 권장"은 처리량이 포화되는 큰 GPU 기준이고, 우리 SLO 구간(처리량 포화 전)에서는 해당되지 않았다.
3. **`max-num-seqs 64`는 SLO 구간(≤8)에선 차이가 없고, 10건/초 이상에서 TTFT가 더 나빠졌다**(@10 779 vs 473 ms, @12 3268 vs 1226 ms). 대기열이 TTFT에 더해진다. 대신 KV 예산이 조금 늘었다(187,536).
4. **결론: 3B에서는 서버 옵션으로 얻을 개선이 없었다.** 기본 설정이 이 부하에서는 이미 가장 좋았다. 한계(약 8~9건/초)는 설정이 아니라 계산량(prefill)이 정한다. 이 해석은 추정이며, prefill/decode 시간을 따로 재서 확인하지는 않았다.

### 3차 결과 (7B, util 0.85, fp16 KV)
| 후보 | KV 총칸 | 정확도 ko/en/전체 | TTFT p95 @2 / @3 / @4 | SLO 통과 |
|---|---|---|---|---|
| C 7B AWQ (기본) | 115,184 | 67/46/56.5 | 298 / - / 850 ms | 2 |
| H 7B AWQ `awq_marlin` 명시 | 115,184 | 67/46/56.5 | 301 / 686 / - ms | 없음 (@2가 301ms로 1ms 초과) |
| I 7B GPTQ-Int4 | 115,296 | 68/50/59.0 | 300 / 679 / 838 ms | 2 (경계) |

3차에서 읽은 것
1. H는 C와 정확도, KV 칸 수, TTFT가 사실상 같다. 기본 AWQ가 이미 marlin 커널을 쓰고 있을 가능성이 높다(추정, 로그에서 커널 이름은 확인하지 못함). 7B가 느린 이유는 커널이 아니라 모델 크기(계산량)로 보인다.
2. GPTQ-Int4는 속도가 AWQ와 같고 정확도는 +2.5%p(59.0 vs 56.5)이지만 200문제 표본에서는 오차 범위 안이다.
3. 7B 계열은 SLO(TTFT p95 300 ms)를 지키는 한계가 약 2건/초로, 3B(약 8건/초)의 1/4이다.

### 아직 모르는 것
- 3B와 7B의 품질 차이가 실제인지 (문제 수를 늘려야 한다: 현재 200문제, ±3.5%p).
- 보정한 fp8 KV(llm-compressor)가 품질을 지키는지.
- 한계를 정하는 것이 prefill인지 decode인지 (단계별 시간은 측정 안 함).
- 이 평가(객관식 컴퓨터과학)가 실제 서비스 질문의 품질을 대표하는지.
- prefix cache가 효과를 내는 현실적 패턴(공통 시스템 프롬프트)은 이번 부하에 없었다.

### 5차 결과: Qwen3.5 계열 비교 (2026-11-02)
조사: Hugging Face API와 모델 카드(ego-browser)로 확인. Qwen 최신 세대는 Qwen3.5/3.6/3.8이고, 16GB에 들어가는 건 Qwen3.5-2B/4B/9B(9B는 양자화 필요). 27B 이상과 35B-A3B는 가중치가 16GB를 넘어 제외. 9B 양자화본은 공식이 아닌 커뮤니티(`cyankiwi` AWQ 4bit)와 Red Hat(`RedHatAI` FP8-dynamic) 것.
조건: 생각 모드 끔(`chat_template_kwargs.enable_thinking=false`, 응답에 생각 내용 없음을 확인), util 0.85, max-model-len 8192, **`--max-num-seqs 128`**(아래 이유), 평가 1,257문제 2회, 부하 도착률 2·3·4/s.

| 모델 | 정확도 ko/en/전체 | 파싱 실패 | 같은 서버 재실행 시 달라진 답 | KV 총칸 | SLO(TTFT p95≤300ms, 1인≥30) |
|---|---|---|---|---|---|
| Qwen2.5-3B (기준) | 58.2/51.1/54.5 | 73 | 1/200* | 177,120 | 8건/초까지 통과 |
| Qwen2.5-7B GPTQ (기준) | 70.2/64.1/67.0 | 0 | 0/200* | 115,296 | 2건/초(p95 300ms, 경계) |
| **Qwen3.5-4B** bf16 | **71.5/67.1/69.2** (2회차 68.8) | 0 | 14/1,257 | 56,971 | 2건/초 통과(p95 198ms), 3건/초 실패(361ms) |
| **Qwen3.5-9B AWQ** 4bit | **76.7/74.4/75.5** (2회차 75.6) | 0 | 6/1,257 | 56,226 | 2건/초에서 p95 336ms로 실패(1인 57 tok/s), 3건/초 780ms |
| Qwen3.5-9B FP8 | - | - | - | - | **시작 실패** |
(* 200문제 평가에서의 값. 1인 tok/s는 낮은 부하에서 4B 51.5, 9B AWQ 57.1, 3B 약 75, 7B GPTQ 약 80.)

확인한 것
1. 최신 세대는 같은 크기에서 정확도가 크게 높다: 4B(69.2%)가 7B GPTQ(67.0%)와 3B(54.5%)를 앞선다. 9B AWQ는 75.5%.
2. 속도는 Qwen2.5보다 느리다: 낮은 부하의 1인 속도가 약 51~57 tok/s(3B 약 75). 4B는 TTFT p95가 7B GPTQ보다 좋았다(2건/초에서 198 vs 300ms).
3. **시작 실패 1: `max_num_seqs (256) exceeds available Mamba cache blocks (135)`** — Qwen3.5는 층의 3/4가 상태 기반(Gated DeltaNet)이라 동시 요청마다 상태 블록이 하나씩 필요하다. 그 블록 수가 모자라 기본 상한 256으로는 시작 불가 → `--max-num-seqs 128`로 해결. 이 오류로 `max_num_seqs` 기본값이 256임이 확인됨(이전엔 추정).
4. **시작 실패 2(9B FP8)**: 기본 설정에서는 CUDA graph 측정 중 `OutOfMemoryError`, `--max-num-seqs 32`는 `No available memory for the cache blocks`, util 0.93에서도 같은 오류. 가중치(FP8 약 10GB 추정) + 비전 인코더 + CUDA graph가 16GB에 맞지 않아 이 GPU에서는 올릴 수 없다고 판단(가중치 정확한 크기는 확인 안 함).
5. 4B는 같은 서버 재실행 시 답이 달라진 문제가 14/1,257(1.1%)로, Qwen2.5의 0건보다 흔들림이 있다(상태 기반 층의 비결정성 가능성은 추정).

한계: 생각 모드를 켠 성능은 측정 안 함(느려짐). 평가는 객관식(컴퓨터과학). 최신 모델은 평가 문제가 학습 데이터에 섞여 있을 가능성을 배제하지 못함. 비공식 양자화본의 품질은 제작자 책임. `max-num-seqs 128`이 이전 측정(256)과 달라 엄밀한 동일 조건은 아님(SLO 구간 동시 요청은 약 10~20개). 부하는 도착률 2~4/s만 측정(Qwen3.5의 상한은 그 근처).
