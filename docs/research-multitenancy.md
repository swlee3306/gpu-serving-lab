# 리서치: 이 제약에서 멀티테넌트 LLM 서빙의 최적 방식은? (2026-11-03)

질문: GPU 1장(GeForce RTX 4070 Ti SUPER, MIG·vGPU 불가)에서 여러 테넌트에게 LLM 서빙을 제공할 때 성능 격리·공정성·과금을 어떤 방식으로 하는 것이 최적인가.
방법: 공식 문서·논문 1차 자료를 직접 읽고(WebFetch/WebSearch), 우리 측정(`step-4-multitenancy.md`)과 대조했다. **"확인함"은 이번에 1차 자료로 읽은 것, "검색 요약"은 검색 결과 요약만 본 것, "미확인"은 못 읽은 것.**

## 1. 목표 범위 (GPUaaS/LLMaaS 플랫폼이 일반적으로 요구하는 것)
- 대규모 GPU를 효율적으로 쓰기 위한 Kubernetes 오케스트레이션과 멀티테넌시 환경
- 멀티테넌트 환경의 네트워크·데이터·모델 격리 설계
- 사용량 기반 과금 로직과 결제 트랜잭션 무결성
- self-healing·failover·rollback 전략, 메트릭·로그·트레이스 통합 관측
- 멀티테넌트 자원 격리·보안·접근 제어

→ LLMaaS는 "API 키 단위 공유 엔드포인트 + 토큰 계량"에 가깝고, GPUaaS는 GPU 자원 단위 제공이다.

## 2. 우리 측정이 말하는 것 (직접 측정)
- 프로세스 단위 GPU 공유(time-slicing, MPS)는 **성능 격리를 못 한다**: 이웃이 있으면 피해자 지연 약 2.05~2.1배(이웃 동시 요청 1개짜리여도 time-slicing에서 3.05s). MPS도 같은 방향이었다(데몬의 기본 활성 스레드 비율은 50.0으로 조회됐으나, 클라이언트에 실제로 적용됐는지와 GPU 활성률은 확인하지 못함).
- 한 엔진을 공유하고 `--scheduling-policy priority`를 쓰면 같은 부하에서 피해자 지연이 5.88s(fcfs) → 2.51s로 줄었다(이웃 처리량 동일). 단, `--max-num-seqs 16`으로 대기열이 생기게 한 설정.
- 쿼터는 GPU 개수만 제한하고 GPU 시간은 제한하지 않는다.

## 3. 후보 방식 비교

| 방식 | 격리 | 이 GPU에서 | 근거 |
|---|---|---|---|
| GPU 통째로 한 테넌트 (패스스루, 전용 노드/엔드포인트) | 가장 강함 | 가능(GPU 2장이 있어 개념 시연만 가능, 4070 Ti는 1장) | 우리 실습(홈랩 일지 3), GPUaaS |
| MIG / vGPU(하드웨어·하이퍼바이저 분할) | 강함 | **불가**(지원 목록에 없음) | 홈랩 일지 5, NVIDIA vGPU 문서 |
| time-slicing / MPS(device plugin) | 약함 | 가능하지만 지연 보장 없음 | 직접 측정, README(replica 간 격리 없음) |
| 소프트웨어 GPU 가상화(HAMi 등) | 메모리 한도 + 컴퓨트 한도(소프트웨어) | 시험 가능성 있음, 미확인 | 아래 3-3 |
| 공유 엔진 + 서빙 층 스케줄링(우선순위, 공정 큐잉) | 요청 단위 공정성 | **가능, 효과 측정함** | 직접 측정 + 아래 3-4 |
| 게이트웨이의 토큰 기반 제한·계량 | 사용량 제어 + 과금 근거 | 가능 | 아래 3-5 |

### 3-1. NVIDIA vGPU 스케줄러 (확인함, NVIDIA vGPU 사용자 가이드)
- 세 정책: **Best effort**(기본, 다른 vGPU가 안 쓰는 사이클을 쓸 수 있음, "그래픽 집약 VM이 가벼운 VM에 영향"), **Equal share**(실행 중인 vGPU에 균등 분할, 다른 vGPU가 시작·종료하면 성능이 변함), **Fixed share**(고정 몫, 다른 vGPU가 시작·종료해도 성능 일정).
- Equal/Fixed share는 엄격한 round-robin이고 끌 수 없다. 정책은 vGPU 생성 전에 설정해야 한다.
- 시사점: 업계도 "공유 GPU의 성능 예측성"을 스케줄러 정책으로 푼다. 이 정책들은 vGPU 대상이라 GeForce에는 적용되지 않는다. 우리 time-slicing이 이 문서의 어느 정책과 같은지는 확인하지 못했다(가설: Best effort/equal share와 비슷한 동작).

### 3-2. KAI Scheduler (확인함, GitHub README)
- 기능 목록: GPU Sharing("multiple workloads to efficiently share single or multiple GPUs"), Time-based fairshare("Over-time fair usage of resources, considering historical usage, time decay"). v0.10.0에 time-based fairshare 포함.
- **README는 GPU 메모리·컴퓨트가 격리·강제되는지 말하지 않는다**(별도 문서에 있을 수 있음, 미확인). 검색 요약에서는 "soft isolation"이라는 서드파티 평가가 있었으나 1차 자료로는 확인하지 못했다.
- 시사점: K8s 스케줄러 층의 공정 분배(큐 단위 몫, 과거 사용량 반영)이지 하드웨어 격리가 아니다.

### 3-3. HAMi / HAMi-core (확인함, GitHub README 두 곳)
- HAMi README: "isolate device memory and compute"(방법·단위 미기술), GeForce 언급 없음.
- HAMi-core README: CUDA 호출을 가로채(`libcudart`와 `libcuda` 사이 "hijacks the API calls") 컨테이너별 메모리 한도와 "SM utilization은 self-implemented time-sharing scheme"으로 컴퓨트 한도를 건다. 설정은 `CUDA_DEVICE_MEMORY_LIMIT`, `CUDA_DEVICE_SM_LIMIT`. 요구: Linux glibc, CUDA 12.x/13.x. 샘플 출력에 GeForce RTX 3060이 나오지만 **지원한다는 진술은 없다**. 정확도·오버헤드·CUDA 경로 전부 커버 여부는 기술되지 않음.
- 검색 요약(서드파티 Cozystack 문서, **미확인**): 컨테이너 OS에 따라 컴퓨트 격리가 조용히 실패할 수 있다(Ubuntu 22.04+ 이미지에서). 우리 vLLM 이미지는 Ubuntu 계열이라 이 위험이 있다.
- 시사점: GeForce에서 컴퓨트 한도를 걸 수 있는 거의 유일한 소프트웨어 후보. **시험해 볼 가치는 있으나 동작 여부·정확도는 직접 재야 안다.**

### 3-4. 서빙 층 공정 스케줄링 (확인함: VTC 논문 초록, llm-d 문서, vLLM 엔진 인자 문서)
- **VTC(Virtual Token Counter)**, OSDI'24 "Fairness in Serving Large Language Models"(arXiv 2401.00588): 요청 수 제한은 "rudimentary notion of fairness"라 용량을 낭비하고, 입력·출력 토큰을 합친 비용으로 공정성을 정의하는 continuous batching 기반 스케줄러를 제안하며, 두 backlogged 클라이언트 사이의 서비스 차이에 "2x tight upper bound"를 증명했다고 주장한다. 초록에는 구체 수치·한계가 없다(전문 미확인).
- **vLLM**: `--scheduling-policy`는 `fcfs`와 `priority`(요청 우선순위 값이 낮을수록 먼저, 같으면 도착 순). 테넌트별 공정 큐잉(VTC 등)이 vLLM에 병합됐다는 근거는 찾지 못했다(검색 요약에서 대학 석사 논문 수준의 시도만 확인).
- **llm-d Flow Control**(문서는 dev 버전, 미출시 문서): 라우터(EPP)가 요청을 `FlowKey = Fairness ID + Priority`로 분류하고 flow별 큐를 두며, 우선순위 밴드(Premium 100, Standard 0, Best-Effort −10)를 높은 쪽부터 서비스하고, 같은 밴드 안의 테넌트는 Fairness Policy로 번갈아 처리한다. 기본은 전역 FCFS에 가깝고 엄격한 공정성은 배치·캐시 재사용 효율을 줄일 수 있다고 문서가 말한다. 또 **테넌트 ID·우선순위를 사용자가 직접 주장하게 두면 남용 경로이므로, 게이트웨이가 API 키나 JWT를 검증해 헤더를 주입해야 한다**고 경고한다. 문서는 벤치마크 도구가 아직 QoS·테넌트 격리를 측정하지 못한다고도 적었다.
- 시사점: 우리가 시험 8에서 쓴 우선순위는 이 구조의 가장 작은 형태다. 공정 큐잉(테넌트 간 균등)은 vLLM 단독으로는 안 되고 라우터/게이트웨이 층이 필요하다.

### 3-5. 게이트웨이의 토큰 기반 제한·계량 (확인함, Envoy AI Gateway 문서를 GitHub 원본에서 확인)
- 테넌트는 `x-tenant-id` 헤더로 구분하고 `Distinct` 셀렉터로 테넌트별 버킷을 만든다. `llmRequestCosts`로 입력·캐시 입력·출력·합계·CEL 토큰 비용을 정의하고, 한도를 넘기면 **HTTP 429**를 돌려준다. Redis와 rate limit이 켜진 Envoy Gateway가 필요하다.
- **중요한 한계(문서)**: 사용량은 **응답이 끝난 뒤** 청구되므로 현재 요청 자신의 토큰은 그 요청의 허용 판단에 반영되지 않고, 이미 허용된 스트림은 중간에 끊지 않는다. 예: 시간당 1,000토큰 한도에서 1,200토큰짜리 스트림이 허용될 수 있다. 즉 이 방식은 **사후 계량·속도 제어**이고 실행 중인 GPU 간섭을 막지는 못한다.
- 주의: 이 문서의 공식 도메인 URL이 다른 도메인(`theagentrouter.ai`)으로 301 리다이렉트되어, 검증되지 않은 리다이렉트를 따르지 않고 공식 GitHub 저장소의 원문 마크다운을 읽었다.

## 4. 종합: 이 제약에서의 최적 방식 (판단)
**한 방식이 아니라 2단 구조가 근거 위에서 가장 합리적이다.** (이것은 위 자료와 우리 측정에서 끌어낸 제 판단이고, 한 번에 검증된 결론은 아니다.)

1. **하드 격리가 필요한 고객 = 전용(Dedicated)**: GPU를 통째로 주는 패스스루/전용 엔드포인트. 우리 측정(time-slicing·MPS 모두 지연 약 2배)이 "프로세스 공유로는 보장이 안 된다"는 근거. GPUaaS에 해당.
2. **일반 고객 = 공유 엔진 + 서빙 층 제어(LLMaaS)**: API 키를 게이트웨이가 검증해 테넌트·우선순위를 주입 → 토큰 기반 한도(Envoy AI Gateway 문서상 응답이 끝난 뒤 사용량을 반영하므로 **사후 계량에 기반한 후속 요청 제한**이다. 엄격한 예산이 필요하면 사전 토큰 예약이나 `max_tokens` 상한을 따로 설계해야 한다) + 엔진 내 우선순위/공정 큐잉(대기열 단계에서 격리) + 토큰 계량(과금). **이 구조는 미검증 설계안이다.** 우리가 측정한 것은 구성 요소 일부뿐이다: 엔진 내 우선순위(시험 8, `--max-num-seqs 16`으로 대기열이 생기는 조건에서만)와 `cache_salt`(캐시 타이밍 신호 한 가지). 게이트웨이 통합, 우선순위 위조 방지, 테넌트 간 공정 큐잉은 구현·시험하지 않았다. 목표 범위의 모델·데이터·네트워크 격리와 사용량 과금에 해당.
3. **프로세스 단위 GPU 공유(time-slicing/MPS)는 지연에 민감하지 않은 배치·개발용에만**, 또는 비용 우선 구간에 쓴다(합계 처리량은 MPS가 더 높았다: 3,300 vs 2,430 tok/s, 이웃 쪽).
4. **하드웨어가 허락하지 않는 부분(MIG, vGPU)**은 설계 문서로 처리하고, 소프트웨어 GPU 가상화(HAMi-core)는 **시험해서 되는지 확인**한다.

## 5. 아직 모르는 것 / 다음에 재야 할 것
- HAMi-core가 GeForce + vLLM 컨테이너(Ubuntu 계열)에서 컴퓨트·메모리 한도를 실제로 거는가, 걸면 noisy neighbor가 풀리는가(가장 싼 시험 후보).
- 시험 8을 **대기열이 없는 설정**(슬롯 여유)과 **테넌트 3개 이상**으로 반복하면 우선순위 효과가 어떻게 달라지는가.
- 테넌트 간 균등을 보장하는 VTC류 공정 큐잉을 직접 구현해 보고(게이트웨이 층, Go/Python), 우선순위만 쓸 때와 비교.
- 토큰 계량의 정확성(재집계, 중복 방지, 스트림 중단)은 Step 5(과금) 과제.
- KAI Scheduler의 GPU sharing 격리 강도, VTC 논문 전문의 한계, 상용 서버리스 추론 서비스들의 실제 격리 방식은 미확인.

### 7-2. 컨테이너 런타임 취약점 CVE-2025-23266 (우리 환경 점검)
- Introl 글은 "NVIDIA는 2025년 1월 27일 ... CVE-2025-23266을 포함한 7건"이라고 쓰지만, 검색으로 본 자료(NVIDIA 공지 미러 CERT 문서, CVE 기록, 보안 업체 글)는 **2025년 7월 공지**이고 **Container Toolkit 1.17.7 이하가 영향**, 수정은 **1.17.8**, GPU Operator는 25.3.1이라고 한다. 글의 날짜는 맞지 않는 것으로 보인다(NVIDIA 공식 페이지는 직접 읽지 못했으므로 **미확인**).
- 우리 gpu-server는 `nvidia-container-toolkit 1.20.1`, `libnvidia-container 1.20.1`(직접 확인, `dpkg`, `nvidia-ctk --version`)이라 영향 범위(≤1.17.7) 밖이다.
- 시사점: 멀티테넌트에서는 컨테이너 런타임 버전 관리가 격리의 일부다. k3s의 nvidia 런타임도 같은 툴킷을 쓴다.

### 7-3. 공유 엔진의 프리픽스 캐시는 테넌트 사이에서 새는가 (직접 측정, `cachesalt.py`)
- vLLM 설계 문서(v0.14.1, 확인함): 요청 본문 최상위에 `cache_salt`를 넣으면 첫 블록 해시에 salt가 들어가서 **같은 salt의 요청끼리만 캐시를 재사용**하고, "타이밍 기반 공격(지연 차이로 캐시된 내용을 추측)"을 막는다고 설명한다. 블록 해시는 SHA256(v0.10.2부터 기본). 현재 최신 문서 페이지(automatic_prefix_caching)에는 이 내용이 없어서 버전별 설계 문서를 근거로 삼았다.
- 시험(공유 vLLM 하나, 프롬프트 약 4,232토큰, `max_tokens=1`이라 지연 ≈ TTFT, 시도 5회, 매번 새 프롬프트, 중앙값):
| 상황 | 지연 p50 |
|---|---|
| A의 첫 요청(캐시 없음) | 340ms |
| **B가 A와 같은 프롬프트, salt 없음** | **25ms** (약 13.6배 빠름) |
| A 첫 요청, salt=tenant-a | 336ms |
| B가 같은 프롬프트, salt=tenant-b | 337ms (캐시 없음과 같음) |
- 해석: salt가 없으면 **B는 지연만으로 "A가 최근에 이 프롬프트를 보냈다"는 사실을 알 수 있다.** 서로 다른 salt를 쓰면 이 신호가 사라졌다. 단, 이것은 **신호가 존재함을 보인 것**이고 실제 공격(B가 프롬프트를 추측해 반복 시도)을 재현한 것은 아니다. 5회 반복에서 값이 일관(25~26ms vs 322~362ms)했으나 한 구성, 한 모델, 한 번의 시험이다.
- 설계 시사점: 공유 엔진에서는 **게이트웨이가 테넌트별 `cache_salt`를 주입**해야 한다. llm-d 문서의 "테넌트 ID를 사용자가 직접 주장하게 두면 남용 경로" 경고와 같은 원칙(클라이언트가 salt를 정하게 두지 않는다). 공유 시스템 프롬프트를 의도적으로 공유하려면 salt를 공유하는 그룹을 정해야 하고, 그만큼 캐시 적중 이득과 격리를 맞바꾼다(위 시험은 이 비용을 재지 않았다).
- 2026년 arXiv 논문(검색 요약, **미확인**)은 루트 salt가 all-or-nothing이라고 비판하며 분기 지점 salt를 제안한다.

### 7-4. 이 보강이 4절 결론에 주는 영향
- 4절의 2단 구조는 그대로이고, 공유 엔진(2단)의 게이트웨이 책임에 **테넌트별 `cache_salt` 주입**(데이터 격리)과 **런타임 패치 관리**가 추가된다.
- 격리 종류(network, data, model isolation) 가운데 **data 격리의 구체적 항목**을 하나 측정으로 확보했다.

### 8-2. 새로 한 시험 두 가지 (gpu-server, Docker, vLLM 이미지 latest, 시험 5와 같은 부하)
**시험 10: time-slice 길이 조절** (`nvidia-smi compute-policy --set-timeslice`, 0=기본 1=짧음 2=중간 3=김. 이 드라이버(580.178.04)의 도움말로 확인)
- 설정은 RTX 4070 Ti SUPER에서 드라이버가 수락했고 `nvidia-smi compute-policy -l`의 조회값도 Short/Medium/Long으로 바뀌었다. 피해자 B(요청 48개, 동시 4)의 지연 p50은 이웃 A(요청 800개, 동시 64)가 있을 때 **기본 3.05s / 짧음 3.06s / 중간 3.06s / 김 3.06s**, 단독은 1.43~1.44s. 이웃 처리량 2,661 / 2,599 / 2,655 / 2,571 tok/s.
- 결론(범위 한정): **이 Docker 구성(`--gpus all`로 컨테이너 둘, 쿠버네티스 device plugin 경로가 아님)과 이 워크로드에서 time-slice 설정값에 따른 지연 변화는 관측되지 않았다.** 정책이 GeForce에서 실제 스케줄링에 영향을 주는지는 확인하지 못했다. 설정 순서는 고정(0→3), 각 값 1회, 이 시험의 vLLM은 0.32.0(digest `sha256:befccf0e...`, 드라이버 580.178.04)이다. 가능한 원인(미검증): 정책이 이 경로에 적용되지 않음, 지속 부하에서 양자 크기 차이가 p50에 드러나지 않음, 꼬리 지연 표본 부족. 정책은 기본값으로 되돌렸다. (원본: `results/timeslice_length.txt`)

**시험 11: vLLM sleep mode로 시간 분할 독점** (공식 문서 확인함: level 1은 가중치를 CPU로 내리고 KV 캐시를 버림, `--enable-sleep-mode`와 `VLLM_SERVER_DEV_MODE=1`, 엔드포인트는 사용자에게 노출하지 말 것). 두 vLLM(A, B)을 모두 띄우고 한 번에 한 쪽만 깨어 있게 번갈아 전환(Docker, vLLM 0.32.0, digest `sha256:befccf0e...`). 전환은 부하가 끝난 뒤 수동 호출이고 진행 중 스트림·동시 전환 경합은 시험하지 않았다.
| 항목 | 값 |
|---|---|
| 재운 인스턴스가 GPU에 남기는 메모리 | 848MiB (깨어 있으면 약 13.2GiB) |
| 첫 번째 sleep 소요 | 5.0s (이후 전환은 0.28s) |
| 이후 전환(재우기 0.28s + 깨우기 0.57s + 첫 요청 0.13s) | 합계 약 0.97s (5회 모두 0.97s, 첫 전환만 5.71s) |
| 깨어 있는 쪽의 부하 지연 p50(요청 48개, 동시 4) | **1.43s** (A와 B 모두, 전환을 3회 오가도 동일) |
- 비교: 같은 GPU를 동시에 쓸 때(time-slicing)는 3.05s. **한 시점에 한 테넌트만 GPU를 쓰면 지연이 단독 기준선과 같았다.** 구조상 동시 실행되는 컨텍스트가 없으므로 컴퓨트·메모리 대역폭 간섭이 없다.
- 대가: 깨어 있지 않은 테넌트는 서비스를 못 받는다(전환 약 1초 + 현재 요청이 끝나길 기다리는 시간). 전환마다 KV 캐시(프리픽스 캐시 포함)가 사라진다. 재운 쪽도 약 850MiB를 점유한다.
- 이번에 **재지 않은 것**: 요청이 진행 중일 때 재우기(드레인 필요), 테넌트 3개 이상, 큰 모델(전환 시간은 가중치 크기에 비례할 것으로 추정, 미측정), 쿠버네티스 위에서의 구성(이번엔 Docker), 재웠을 때 KV 캐시 메모리가 지워지는지(문서는 "discard"라고만 함). (원본: `results/sleepmux.txt`)

### 8-3. 조합 평가 (이 하드웨어: GPU 1장, GeForce)
격리 강도는 "같은 순간에 같은 GPU를 쓰는가"로 갈린다. 아래는 근거(조사+측정)에서 끌어낸 제 판단이다.
| 조합 | 성능 격리 | 데이터 격리 | 동시 서비스 | 이 GPU에서 | 평가 |
|---|---|---|---|---|---|
| 전용 GPU(패스스루/전용 노드) | 완벽(하드웨어) | 강함 | 테넌트 수 = GPU 수 | GPU 2장이 있어도 4070 Ti는 1장 | 가장 확실, 가장 비쌈 |
| **시간 분할 독점(sleep mode 전환, 서비스 정책)** | **관측: 기준선과 같음(1.43s, 이 구성에서). 하드웨어 격리는 아님** | 문서상 KV 폐기, GPU 메모리 잔존 데이터가 실제로 초기화되는지는 미측정 | 한 번에 한 테넌트 | **가능, 직렬 전환만 측정함** | 이 구성에서 기준선 수준 지연. SLA 보장은 후속 검증(드레인, 잠금, 큰 모델) 전까지 할 수 없음. 소수 테넌트, 버스트형 트래픽 후보 |
| 공유 엔진 + 우선순위 + cache_salt + 토큰 한도·계량 | 부분(측정: 1.44 → 2.51s, fcfs 5.88s) | salt로 캐시 타이밍 신호 제거(측정) | 다수 | **가능, 측정함** | 동시 서비스·과금에 가장 맞음, 잔여 간섭 있음 |
| time-slicing / MPS / time-slice 길이 | 없음(측정: 약 2.1배, 길이 무관) | 약함(메모리 격리 없음) | 다수 | 가능 | 지연이 중요하지 않은 내부 배치·개발용 |
| 소프트웨어 GPU 가상화(HAMi-core) | **시험함(13절)**: 메모리 한도는 강제됨, 컴퓨트 한도는 CUDA graph를 끈 eager 모드에서만 걸리고 부분 보호(이웃 25%: 피해자 1.4~1.55배, 10%: 1.28배) | 메모리 한도 강제 | 다수 | **GeForce에서 동작 확인**, 컨테이너마다 `LD_PRELOAD` 필요 | 이웃을 줄이는 방식이라 피해자 보호는 부분적, vLLM 기본(graph)에서는 컴퓨트 한도 무효 |
| 하드웨어 분할(MIG, AMD CPX/MxGPU) | 강함(단 PCIe·장애 도메인 한계) | 강함 | 다수 | **불가** | 장비 제약으로 설계 문서화 |

### 8-4. 결론 (최적 조합, 이 제약에서)
0. **용어 구분**: (가) **하드웨어 자원 분할**(전용 GPU, MIG, AMD CPX/MxGPU)은 같은 순간에 자원이 물리적으로 나뉜다. (나) **직렬화 정책**(한 번에 한 테넌트만 실행)은 자원을 나누지 않고 시간을 나눈다. 둘은 "격리"의 의미가 다르다. 또 "전용 엔드포인트"가 "전용 GPU"를 뜻하는 것은 아니다.
1. **이 하드웨어에서 (가)는 확인하지 못했다.** 하드웨어 분할은 전용 GPU(테넌트당 1장), MIG, AMD CPX/MxGPU의 영역인데 우리는 해당 장비가 없다(MIG는 이 GPU의 공식 지원 목록에 없음). 소프트웨어로 같은 순간에 나눠 쓰는 방식(time-slicing, MPS, time-slice 길이 설정)은 우리 시험(각 구성 1~몇 회, 테넌트 2개)에서 지연 약 2배를 막지 못했다.
2. **우리 시험에서 같은 순간 간섭을 없앤 유일한 방법은 (나) 시간으로 나누는 것이었다.** sleep mode로 한 번에 한 테넌트만 깨우자 깨어 있는 쪽의 지연 p50이 단독 기준선과 같았고(1.43s, 3B 모델, 요청 48개·동시 4, 전환 몇 차례 관찰), 전환은 약 1초였다. 이것은 "이 구성에서 관찰된 값"이고 SLA 보장은 아니다(큰 모델, 도착 폭주, p99, 장애, 진행 중 요청 처리는 미측정). 대가는 동시 서비스를 못 하는 것이다.
3. **그래서 최적은 한 방식이 아니라 SLA 등급별 조합**이다.
   - **등급 1 (보장형, 소수 테넌트)**: 전용 GPU. GPU가 부족하면 **시간 분할 독점**(sleep mode)으로 같은 GPU를 시간표로 나눈다. 지연 보장 필요 고객용.
   - **등급 2 (공유형, 다수 테넌트)**: **공유 엔진 + 게이트웨이**(API 키 검증 → 테넌트 ID·우선순위·`cache_salt` 주입 → 토큰 기반 한도 → 엔진 내 우선순위 → 토큰 계량). 동시 서비스와 과금에 맞고 잔여 간섭을 SLO에 반영.
   - **등급 3 (내부·개발용)**: time-slicing/MPS. 지연 보장 없음.
   - 공통: 쿼터·NetworkPolicy·RBAC·Pod Security(홈랩 일지 13), 런타임 패치 관리.
4. **아직 모르는 것, 시험해야 확정되는 것**: HAMi-core의 컴퓨트 한도가 GeForce+vLLM에서 실제로 걸리는가(걸리면 등급 2의 잔여 간섭을 줄일 수 있음), sleep mode 전환 시 진행 중 요청과 큰 모델에서의 전환 시간, 테넌트 3개 이상, 쿠버네티스 위 구현, sleep 시 GPU 메모리 잔존 데이터가 실제로 지워지는가(문서는 KV 캐시를 "discard"한다고만 함), 진행 중 요청 드레인과 단일 활성 테넌트를 보장하는 잠금(lease), 동시 전환 경합, 이미지 digest·드라이버·CUDA 버전 고정.
5. 포트폴리오 관점의 서술(범위 한정): "하드웨어가 허락하지 않는 격리(MIG, vGPU)는 설계로 문서화하고, **실제로 확인한 항목**(RBAC, ingress NetworkPolicy, Pod Security, prefix-cache 타이밍 신호와 `cache_salt`, 엔진 내 우선순위, sleep mode 직렬 전환)만 측정 사례로 제시한다"가 근거와 맞는다. egress 차단, 서비스 인증, 저장소·모델 격리, 메모리 격리, 게이트웨이 통합은 미시험이므로 설계·후속 과제로 표시한다.

### 11-2. 토론에서 Claude가 틀렸던 것
- **R2-2의 논리 오류**: "이웃 부하가 40분의 1(동시 64 → 1)로 줄어도 지연이 같으니 자원 경합이 아니다"라고 했으나, **tok/s는 자원 사용량이 아니다.** 배치 1 decode는 토큰마다 가중치를 읽어 메모리 대역폭을 많이 쓴다(단독 91 tok/s × 약 6.2GB ≈ 565GB/s, 이론 672GB/s의 약 84%, 추정). 같은 계산으로 동시 64(약 2,900 tok/s)는 약 280GB/s다. 즉 동시 1 이웃이 "가볍다"는 전제가 틀릴 수 있다. 이 계산은 가정이 많은 추정이다.
- **새 해석(미검증, 12절의 합성 이웃 실험에서 기본 모드에 한해 약해짐)**: 피해자(동시 4, 355 tok/s ≈ 약 550GB/s ≈ 이론의 약 82%)도 이미 대역폭 한계 근처에서 돌고 있어서, 대역폭을 많이 쓰는 이웃이 하나만 있어도 각자 절반 수준이 되는 것(약 2배)은 **컨텍스트 시간 분할 없이도** 설명된다. 이 설명이 맞다면 MPS의 SM 분할이 소용없고 time-slice 길이가 무관했다는 결과와도 맞고, 하드웨어 수준에서 대역폭을 나누는 방식(MIG 등)만 이 문제를 풀 수 있다는 뜻이 된다. 반대로 시간 분할 설명이 맞다면 sleep mode 같은 직렬화가 답이다. **현재 데이터로는 둘을 구분하지 못한다.**
- **직접 측정한 보조 증거(결정적이지 않음)**: NVML `utilization.memory`는 동시 4/1/16/64에서 94/99/97/94%, 전력 183/211/202/215W(`results/bwprobe.txt`). 이 지표는 "메모리가 바빴던 시간 비율"이라 포화를 뜻하지 않는다(시리즈 11편의 GPU 사용률 100% 교훈과 같은 함정). 다만 단독 단일 스트림이 동시 64와 비슷한 전력(211W 대 215W)을 쓴 점은 "동시 1 이웃은 가볍다"는 전제를 약하게 만든다.
- **문서 오류 정정**: 동시 1 이웃 시험의 피해자 요청 수는 32개(문서는 48개로 적어 둠), 피해자 단독 기준선이 "이웃 엔진이 떠 있되 유휴" 상태였다는 점이 문서에 없었다. 시험 7 기록에 반영했다.

### 11-3. 끝까지 남은 불일치·미해결
1. **time-slicing/MPS에서 지연 2배의 원인**(12절에서 부분 해결: 기본 모드는 컨텍스트 교대 쪽을 지지, MPS 모드는 실험이 불안정해서 미해결): "활성 컨텍스트 교대" vs "메모리 대역폭 공유". 구분하는 결정적 실험은 이웃을 합성 부하로 대체하는 것이다: 이웃이 (가) 메모리 대역폭만 쓰는 복사 루프, (나) 연산만 쓰는 GEMM 루프, (다) 유휴일 때 피해자 지연을 비교하고, 가능하면 프로파일링 지표(예: DCGM의 DRAM active 계열, GeForce 지원 여부는 미확인)를 함께 본다. (가)만 지연을 키우면 대역폭 공유, (나)도 키우면 시간 분할이다.
2. 시험 8의 효과가 B 부하가 커질 때(기아·재분배)와 다른 `max-num-seqs`, 다른 도착 순서에서도 유지되는가.
3. 설계 이분법(프로세스-per-테넌트 vs 공유 엔진) 외에 **테넌트 그룹별 엔진**(유사 SLA·신뢰 수준끼리 엔진 공유, 그룹 간 엔진 분리)이 의미 있는 중간안인가. 모델 메모리가 그룹 수만큼 늘고 그룹 내 데이터 격리 문제는 남는다. 미시험.
4. 그 밖에 시험 5·7 구성의 `max-num-seqs=256` 기본값은 문서에 기록되지 않았고 0.33.0 소스로는 확인하지 않았다(Codex 지적). B 동시성 4가 어떤 현실적인 기본값보다도 작아서 결론에는 영향이 없다고 본다.

### 11-4. 토론이 바꾼 결론
- 8-4의 "같은 순간 간섭을 없앤 유일한 방법은 시간으로 나누는 것"은 **"이 구성에서 관찰된 유일한 방법"**으로 유지하되, 같은 순간 공유가 실패한 이유가 시간 분할 때문인지 대역폭 때문인지는 **열린 질문**으로 격하한다. 후자라면 소프트웨어 SM/시간 한도(MPS, HAMi-core의 컴퓨트 한도)는 이 문제를 풀 수 없을 가능성이 커서, HAMi-core 시험의 기대치도 낮춰야 한다(메모리 한도는 가능).
- 다음 시험 순서: (1) 합성 이웃 실험(원인 구분, 반나절 이내, 결론의 해석을 바꿈), (2) 게이트웨이 PoC(주 트랙), (3) HAMi-core 호환성 스모크 테스트(통과 기준: 로드 확인과 실제 한도 반영 확인을 구분), (4) sleep mode 확장.

## 12. 합성 이웃 실험: 지연 2배의 원인 구분 (2026-11-03)
토론(11절)에서 남은 첫 번째 불일치("활성 컨텍스트 교대" vs "메모리 대역폭 공유")를 가르기 위한 시험. 이웃을 vLLM 대신 합성 부하로 바꿨다. 원본: `results/synth_neighbor_default.txt`, `results/synth_neighbor_mps_partial.txt`, `results/mps_fault_evidence.txt`, 스크립트 `results/scripts/{nbr.py,synth.sh,synth_mps.sh,run_mps.sh}`.

### 12-1. 구성
- 피해자 B: vLLM 0.32.0(Docker, digest `sha256:befccf0e...`, util 0.48), 요청 48개·동시 4·128토큰. 이웃은 별도 컨테이너·별도 CUDA 컨텍스트.
- 이웃 유형(`nbr.py`, PyTorch): **idle**(컨텍스트와 1GiB 버퍼만 보유), **copy**(1GiB→1GiB 복사 반복, 메모리 대역폭만 소모), **gemm**(8192×8192 fp16 행렬 곱 반복, 연산 위주). 듀티 사이클 100%와 25%(100ms 주기 중 25ms만 가동).
- 이웃 단독 성능(직접 측정): copy 610GB/s(이론 672GB/s의 약 91%), gemm 90.9 TFLOP/s, 듀티 25%일 때 평균 172GB/s·22.0 TFLOP/s. 가동 중에는 각각 608GB/s·85.3 TFLOP/s.
- 순서: 정방향 한 번과 역방향 한 번(순서 효과 확인).

### 12-2. 기본(시간 분할) 모드 결과 (유효)

| 없음(기준선 2회) | 1.43 / 1.47~1.59s | 1.00 | 354~356 tok/s |
| idle(컨텍스트만 보유) | 1.44 / 1.48~1.49s | 1.01 | 356 tok/s |
| copy 100% | 2.97 / 3.02s | **2.08배** | 172 tok/s |
| **gemm 100%** | **3.21~3.22 / 3.27s** | **2.24배** | 159 tok/s |
| copy 25% | 1.71 / 1.77~1.78s | 1.20배 | 298 tok/s |
| gemm 25% | 1.99 / 2.03s | 1.39배 | 257 tok/s |
- 정방향과 역방향 패스의 값이 소수 둘째 자리까지 같아서 순서 효과는 보이지 않았다.
- **연산만 쓰는 이웃(gemm)이 대역폭 이웃(copy)보다 피해자를 같거나 더 느리게 했다(2.24배 vs 2.08배).** 순수한 메모리 대역폭 공유가 지배적 원인이라면 DRAM을 적게 쓰는 행렬 곱 이웃의 영향이 훨씬 작아야 한다. 이 결과는 "활성 이웃이 있으면 GPU를 번갈아 독점한다"(기본 모드의 시간 분할)는 설명을 지지하고, 11절의 "대역폭 공유" 새 해석은 **기본 모드에서는 약해졌다**. 단 GEMM의 실제 DRAM 사용량은 측정하지 않았다(카운터 없음).
- idle 이웃은 영향이 없다: **활성 이웃이어야 한다**(11절 R2-2의 "유휴 기준선" 가정이 이번에 직접 확인됨).
- **이웃의 가동률(GPU가 바쁜 시간 비율)을 낮추면 간섭이 줄었다**: 100%에서 2.08~2.24배, 25%에서 1.20~1.39배. 순수 독점 교대 모델의 예측(이웃이 25% 시간 점유하면 피해자 약 1.33배)과 대략 맞는다. 즉 간섭의 크기는 이웃의 tok/s가 아니라 **GPU가 바쁜 시간 비율**을 따라간다. 앞서 동시 1개 vLLM 이웃(74 tok/s)이 동시 64개(약 2,900 tok/s)와 같은 지연(3.05 vs 3.06s)을 만든 것도 이웃의 연속 디코딩이 둘 다 GPU를 거의 항상 바쁘게 만들기 때문으로 읽힌다(NVML util.gpu 94~98%).
- 한계: 한 GPU, 한 모델, 정방향·역방향 각 1회, 이웃은 합성 부하(실제 서빙 이웃과 커널 길이·패턴이 다름), 듀티 사이클은 이웃이 스스로 쉬는 것이지 강제 제한이 아님.

호스트에서 `nvidia-cuda-mps-control -d`를 띄우고 컨테이너 둘에 `/tmp/nvidia-mps`를 마운트해 같은 실험을 했다.
| 이웃 | B 지연 p50 / p95 | 비고 |
|---|---|---|

| copy 100% | 1.46 / **96.61s** (벽시계 126.6s) | p50은 정상, 요청 3개가 약 100초 정지 |
| gemm 100% | 1.46 / **110.94s** (벽시계 127.0s) | 같은 양상 |

- **역방향 패스 시작 때 피해자 vLLM이 죽었다**(`HTTP 500`, 컨테이너 소멸). 커널 로그 `NVRM: Xid 31 ... name=VLLM::EngineCor ... MMU Fault`(15:06:22)와 MPS 서버 로그 "Client {PID: 1404799} encountered a fatal GPU error ... torn down"(15:06:33)로 피해자 엔진 프로세스가 GPU 오류로 끝난 것을 확인했다(`results/mps_fault_evidence.txt`). 장치 플러그인이 건강 검사에서 무시하는 Xid 목록(13, 31, 43, 45, 68, 109)에 31이 들어 있다는 점(홈랩 일지 8의 로그)도 같이 기록해 둔다.

- **원인 불명**: 오류의 원인이 MPS 자체인지, 이웃을 `docker kill`로 강제 종료한 영향인지, 호스트 MPS와 Docker 구성(IPC 공유, 파이프 마운트)인지, 합성 이웃의 메모리 접근인지 구분하지 못했다. 앞서 쿠버네티스 Helm MPS 시험(vLLM 이웃)에서는 이런 오류가 없었다. 따라서 **MPS가 일반적으로 불안정하다고 결론 내리지 않고**, "이 구성에서 정지와 GPU 오류가 발생해 MPS 모드 비교는 성립하지 않았다"로 기록한다.
- 따라서 "동시 실행 모드(MPS)에서 대역폭이 원인인가"는 **미해결**이다.

### 12-4. 이 실험이 바꾸는 것
- 11-2의 "대역폭 공유" 새 해석은 기본 모드에서 약해졌고, 원래 가설(활성 이웃이 있으면 번갈아 실행)이 더 유력해졌다. 둘 다 아직 "가설"로 표기한다(DRAM 카운터 없음, 합성 이웃, 각 1회).
- **HAMi-core 시험의 기대치를 되돌린다**(11-4에서 낮춘 것을 철회): 간섭이 이웃의 GPU 점유 시간 비율에 비례하므로(25%에서 1.2~1.4배, 100%에서 2.1~2.2배), 이웃의 가동 시간을 제한하는 소프트웨어(HAMi-core의 컴퓨트 한도는 문서상 "self-implemented time-sharing")는 원리상 효과가 있을 수 있다. 단 듀티 사이클 시험은 이웃이 자발적으로 쉰 것이지 강제 제한이 아니므로 HAMi-core가 실제로 그렇게 동작하는지는 별도 시험이 필요하다.
- 설계 시사점: 같은 GPU를 쓰는 이웃은 "얼마나 많이 처리하는가"가 아니라 "GPU를 얼마나 바쁘게 점유하는가"로 계량·제한해야 한다. 과금과 한도의 기준 후보로 **GPU 점유 시간(바쁜 시간)** 이 토큰 수보다 간섭을 잘 설명한다(이 구성에서의 관찰).
- 남은 불확실: 동시 실행(MPS) 모드의 원인 구분, 이웃 유형(실제 서빙 부하) 다양화, 반복 횟수.

| D. vLLM 호환 | 메모리 10g 한도 + util 0.85에서 기동·서빙(KV 50,048토큰), 지연 p50 1.43s(기준선과 동일) |

### 13-3. 합성 이웃에 한도를 건 시험 (이웃=gemm/copy, 피해자 vLLM은 HAMi 없음)
| 이웃 | 이웃 처리량 | 피해자 B p50 | 기준선(1.43s) 대비 |
|---|---|---|---|
| gemm, 한도 없음 | 65.3 TFLOP/s | 3.20s | 2.24배 |
| gemm, SM 50% | 44.3 | 3.21s | **2.24배(개선 없음)** |
| gemm, SM 25% | 21.2 | 1.87s | 1.31배 |
| gemm, SM 10% | 8.6 | 1.61s | 1.13배 |
| copy, 한도 없음 / SM 25% | 444 / **443 GB/s** | 2.96 / 2.96s | **한도가 걸리지 않음** |
- 이웃 처리량은 한도에 비례했다(49%, 23%, 9.4%). 그러나 피해자 보호는 **비선형**이다: 50%에서는 전혀 개선이 없고 25% 이하에서만 효과가 있었다.
- copy 이웃에 SM 한도가 걸리지 않은 이유는 `y.copy_(x)`가 커널이 아니라 메모리 복사(`cudaMemcpyAsync`)로 실행돼서라는 **추정**이다(미확인). 소스상 `rate_limiter`는 커널 실행 후킹에서만 호출된다.

### 13-4. 실제 서빙 이웃(vLLM)에 한도를 건 시험
피해자 B는 HAMi 없는 vLLM(util 0.48, 요청 48개·동시 4). 이웃 A는 HAMi 아래 vLLM(메모리 한도 8000m, util 0.95, 동시 16). 이웃의 처리량은 A의 `/metrics`(`vllm:generation_tokens_total`)로 B 실행 구간에서 쟀다.
- **첫 시도는 전부 실패**(데이터 없음): 이웃 vLLM이 기동하지 못했다. 원인은 `Free memory on device cuda:0 (7.22/7.42 GiB) on startup is less than desired GPU memory utilization (0.98, 7.27 GiB)`(한도 7600m와 util 0.98이 너무 빠듯). 한도를 8000m, util을 0.95로 고쳤고, 컨테이너가 죽으면 즉시 실패하도록 대기 루프도 고쳤다.
| 이웃 vLLM | SM 한도 | B 지연 p50 | 이웃 처리량 |
|---|---|---|---|
| **CUDA graph(기본)** | 없음 / 50 / 25 / 10 (정방향·역방향, 7회) | **전부 3.10s** (2.17배) | **전부 663~664 tok/s** |
| **eager(`--enforce-eager`)** | 없음 | 3.12s (2.18배) | 659 tok/s |
| eager | 25% | 2.01s (1.41배) / 재현 2.22s (1.55배) | 388 / 406 tok/s (한도 없음의 59~62%) |
| eager | 10% | 1.83s (1.28배) | 220 tok/s (33%) |
- **vLLM 기본(CUDA graph)에서는 HAMi의 SM 한도가 전혀 적용되지 않았다**(이웃 처리량이 한도와 무관). 소스에서 원인이 확인된다: `cuGraphLaunch`는 후킹되지만 `LOG_DEBUG` 뒤 그대로 통과시키고(`src/cuda/graph.c:291~293`), `rate_limiter`는 `cuLaunchKernel`, `cuLaunchKernelEx`, `cuLaunchCooperativeKernel`에서만 호출된다(`src/cuda/memory.c`). vLLM 디코딩은 CUDA graph로 실행된다.
- **CUDA graph를 끄면(`--enforce-eager`) 한도가 걸렸다.** 이 가설은 시험으로 확인됐다.
- 이웃 처리량은 한도 비율보다 덜 줄었다(25% → 59~62%, 10% → 33%). 한도는 SM 사용률 기준이고 이웃 디코딩이 SM을 가득 쓰지 않기 때문으로 **추정**한다(미확인).

### 13-5. 해석과 한계
- **결론(이 구성에서)**: HAMi-core는 GeForce와 CUDA 13에서 동작하고 메모리 한도를 강제한다. 컴퓨트 한도는 행렬 곱에는 정확히 걸리지만 vLLM에서는 **CUDA graph를 끈 경우에만** 걸리며, 걸려도 피해자 보호는 **부분적**이다(이웃 25% → 1.41~1.55배, 10% → 1.28배, 한도 없음 2.18배). 단독 실행 기준선(1.0배)에는 못 미친다.
- **맞교환**: 이웃을 25%로 제한하면 이웃 처리량이 약 60%, 10%면 약 33%로 줄고, 피해자는 1.3~1.5배까지 보호된다. sleep mode의 시간 분할 독점(피해자 1.0배, 이웃은 정지)과 다른 지점의 맞교환이다.
- **eager 모드의 비용은 측정하지 않았다**: CUDA graph를 끄면 vLLM 자체 디코딩 성능이 떨어질 수 있다(이웃의 단독 처리량, 피해자에 쓸 경우 모두 미측정).
- 한계: 대부분 각 구성 1회(eager 25%만 2회, 1.41배와 1.55배로 달랐다), 이웃은 동시 16 하나, 피해자는 HAMi 없음, vLLM 0.32.0 하나, 쿠버네티스 통합(HAMi의 device plugin이 `LD_PRELOAD`와 한도를 주입하는 방식)은 시험하지 않았다. 컨테이너마다 `LD_PRELOAD`가 필요하므로 이웃이 협조하지 않는 환경(테넌트가 자기 컨테이너를 통제)에서는 플랫폼이 강제로 주입해야 한다.
- 설계 시사점: (1) 등급 2(공유형)에서 **베스트 에포트 테넌트를 25% 이하로 제한**하는 방식은 가능하지만 vLLM의 CUDA graph를 끄는 대가가 있다. (2) 50:50 같은 "공평한" 분할은 피해자를 보호하지 못했다. (3) 시간 분할 독점(sleep mode)과 이웃 제한(HAMi, eager)은 서로 다른 SLA 등급의 도구로 보는 것이 맞다.
