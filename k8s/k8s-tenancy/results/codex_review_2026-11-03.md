두 문서와 관련 실험 원본·스크립트를 읽기 전용으로 대조했습니다. 주요 수정 지점은 **측정 결과의 표현 범위를 좁히고, 서로 다른 격리 개념을 분리하는 것**입니다.

## 1. 사실·표기와 결론의 강도

- **위치:** [리서치 §8-2, 시험 10](<../../../docs/research-multitenancy.md>)  
  **문제:** “GeForce에서 값이 실제 반영됐는지 확인하지 못했다”는 표현이 원본 로그보다 약합니다.  
  **근거:** [원본 출력](<timeslice_length.txt>)에는 설정 성공과 `nvidia-smi compute-policy -l`의 각 값이 기록돼 있습니다. 런타임 스케줄링에 효과가 있었는지는 별도 문제입니다.  
  **제안:** “드라이버가 설정을 수락하고 조회값도 바뀌었으나, GeForce에서 실제 스케줄링 동작에 영향을 줬는지는 확인하지 못했다”로 구분하세요.

- **위치:** [리서치 §8-2~8-4](<../../../docs/research-multitenancy.md>)  
  **문제:** sleep mode의 KV 설명이 서로 충돌합니다. “전환마다 캐시가 사라진다”와 “KV 캐시 메모리가 지워지는지는 미측정”이 함께 쓰였습니다.  
  **근거:** 원본은 재운 뒤 GPU 메모리 848MiB가 남았다고 기록합니다. 문서상의 KV 폐기와 메모리의 안전한 초기화는 같은 사실이 아닙니다.  
  **제안:** “vLLM이 KV 캐시를 폐기한다고 문서화돼 있다”와 “GPU 메모리의 잔존 데이터가 실제로 초기화됐는지는 미측정”을 분리하세요.

- **위치:** [리서치 §8-3~8-4](<../../../docs/research-multitenancy.md>)  
  **문제:** `1.43s = 기준선`을 “완벽한 성능 격리”와 “지연 보장”으로 확대했습니다.  
  **근거:** [원본 sleep 로그](<sleepmux.txt>)는 Qwen 2.5 3B, 요청 48개·동시 4의 p50/p95를 전환 몇 차례 관찰한 결과입니다. 큰 모델, 도착 폭주, p99, 장애 상황은 측정하지 않았습니다.  
  **제안:** “이 구성에서 다른 인스턴스를 sleep 상태로 둔 동안 관측한 지연은 기준선과 비슷했다”로 한정하고, SLA 보장은 후속 검증 항목으로 남기세요.

- **위치:** [리서치 §8-1 AMD 행](<../../../docs/research-multitenancy.md>)  
  **문제:** 특정 회사 제품에 관한 문장이 표 안에 출처 없이 들어 있습니다. MI300X 분할 설명과 MI350X의 MxGPU 이슈도 같은 행에 있어 제품 세대가 혼동될 수 있습니다.  
  **근거:** 문서의 참고 목록만으로는 회사 제품 주장의 출처를 찾기 어렵습니다. 외부 자료는 이번 범위에서 다시 확인하지 않았습니다.  
  **제안:** 회사 제품 주장은 출처를 붙이거나 “검색 요약/미확인”으로 표시하고, MI300X와 MI350X 관련 내용을 분리하세요.

## 2. 시험 설계와 해석

- **위치:** [실습 §시험 8](<../../../docs/step-4-multitenancy.md>)  
  **문제:** `--max-num-seqs 16`과 실행 순서가 결과를 좌우합니다. 우선순위 시험을 일반적인 간섭 완화나 공정성의 증거로 확대하면 안 됩니다.  
  **근거:** [`prio.sh`](<../prio.sh>)는 A의 부하를 먼저 시작하고 8초 뒤 B를 보냅니다. 16개 제한으로 대기열이 쌓이는 조건에서 FCFS p50 5.88초가 priority p50 2.51초로 줄었습니다. 이 결과는 **대기 중 요청의 순서 조정 효과**를 보여주지만, 슬롯이 충분할 때나 대기열이 없는 경우는 시험하지 않았습니다.  
  **제안:** 현재 결론을 해당 조건의 대기열 효과로 제한하세요. 여러 `max-num-seqs` 값, 부하 도착 순서, 반복 측정과 함께 테넌트별 p95/p99·기아 여부를 비교하세요.

- **위치:** [실습 §시험 6~7](<../../../docs/step-4-multitenancy.md>)  
  **문제:** “이웃의 존재만으로 지연이 정해진다”는 해석은 아직 가설입니다. MPS와 time-slicing의 직접 비교도 설정이 달라 일반화하기 어렵습니다.  
  **근거:** time-slicing의 B p50은 A 처리량 약 74~2,924 tok/s에서 대체로 3.05~3.10초였습니다. 이는 가설과 맞지만 각 부하 조건이 1회이고 요청 동시성은 GPU 활성률 자체가 아닙니다. MPS와 time-slicing은 설정된 replica 수도 각각 2와 4이며, 로그에는 실제 GPU 활성률이 없습니다.  
  **제안:** “이 네 부하 조건에서 B 지연이 비슷했다”고 기록하고, 반복 측정과 GPU 사용률·클록·활성 시간 관측을 추가하세요. 원본에 기록된 MPS 활성 스레드 비율 50.0만으로 고정된 50:50 SM 분할을 확인했다고 표현하기도 어렵습니다. 이 의미는 **확신 낮음**이며 드라이버 동작을 독립 검증하지 않았습니다.

- **위치:** [리서치 §8-2 시험 10](<../../../docs/research-multitenancy.md>)  
  **문제:** 결과를 “time-slice 길이는 영향 없음”으로 넓히기 어렵습니다.  
  **근거:** [`ts_len.sh`](<scripts/ts_len.sh>)는 Kubernetes device-plugin 시험이 아니라 Docker의 `--gpus all`로 두 컨테이너를 실행합니다. 정책 순서도 고정이고 각 값은 한 번씩 시험했습니다. 설정값별 p50 차이가 거의 없다는 것만 확인됩니다.  
  **제안:** “이 Docker 구성과 워크로드에서 지연 변화가 관측되지 않았다”고 한정하세요. 가능한 원인은 device-plugin time-slicing과 다른 경로를 시험했거나, 지속 부하에서 양자 크기 차이가 p50에 드러나지 않았거나, 반복·꼬리 지연 표본이 부족한 경우입니다.

- **위치:** [실습 §시험 10~11, 한계](<../../../docs/step-4-multitenancy.md>)  
  **문제:** sleep mode 시험은 직렬 전환 성능을 봤지만, 실제 독점 제어를 검증하진 않았습니다.  
  **근거:** [`sleepmux.sh`](<scripts/sleepmux.sh>)는 요청 부하가 끝난 뒤 수동으로 재우고 깨웁니다. 진행 중 스트림, 동시 wake 요청, 테넌트별 큐, 전환 장애는 시험하지 않았고 Kubernetes 구성도 아닙니다.  
  **제안:** SLA에 쓰기 전에 요청 드레인, 단일 활성 테넌트를 보장하는 lease/잠금, 동시 전환 경합, 큰 모델과 Kubernetes에서의 대기시간을 시험하세요. 또 시험 매니페스트와 스크립트가 `vllm/vllm-openai:latest`를 사용하므로 재현성을 위해 이미지 digest와 드라이버·CUDA 버전을 고정하는 편이 좋습니다.

## 3. 논리 비약과 SLA 조합

- **위치:** [리서치 §8-3~8-4](<../../../docs/research-multitenancy.md>)  
  **문제:** “같은 순간에 완벽한 격리는 불가능”과 “한 GPU의 완벽한 성능 격리는 시간 분할만 가능”이 격리의 뜻을 달리 쓰며, 표는 sleep mode에 “완벽”을 부여합니다.  
  **근거:** 실험은 작은 동일 모델을 번갈아 서비스할 때의 지연을 측정했습니다. GPU 메모리·데이터 초기화, SLA 보장, 동시 요청 통제는 검증하지 않았습니다.  
  **제안:** **하드웨어 자원 분할**과 **한 번에 한 테넌트만 실행하는 서비스 정책**을 별도 항목으로 정의하세요. 현재 결론은 “이 GPU에서 하드웨어 분할을 확인하지 못했고, 한 워크로드의 직렬 서비스에서는 기준선과 비슷한 지연을 관측했다” 정도가 맞습니다. 전용 엔드포인트 자체도 전용 GPU를 뜻하지 않으므로 둘을 구별해야 합니다.

- **위치:** [리서치 §3-4, §4, §8-4](<../../../docs/research-multitenancy.md>)  
  **문제:** 우선순위 스케줄링을 공정 큐잉과 가까이 묶고, 공정 큐잉은 게이트웨이 층만 필요하다고 결론 내립니다. 우선순위는 공정성 보장이 아니며, VTC 같은 스케줄러는 엔진 내부에 구현할 수도 있습니다.  
  **근거:** 시험 8은 요청 `priority`를 클라이언트가 직접 보내고, 게이트웨이는 구현하거나 시험하지 않았습니다. `cache_salt` 시험도 프리픽스 캐시 타이밍 신호 한 가지에 한정됩니다.  
  **제안:** 표의 “공유 엔진 + 게이트웨이”는 “검증된 구성”이 아니라 **우선순위·cache_salt의 개별 실험에 기반한 미검증 설계안**으로 표시하세요. 테넌트별 가중 공정 큐잉은 게이트웨이·라우터 또는 엔진 스케줄러 확장 중에서 선택할 수 있습니다.

- **위치:** [리서치 §3-5, §4, §8-4](<../../../docs/research-multitenancy.md>)  
  **문제:** “토큰 기반 한도”를 사전의 엄격한 한도처럼 제시합니다.  
  **근거:** 같은 문서가 Envoy AI Gateway 사용량을 응답 종료 뒤 반영하고, 현재 요청의 토큰은 허용 판정에 포함되지 않으며 스트림도 중간 종료하지 않는다고 설명합니다.  
  **제안:** 이를 사후 계량·후속 요청 제한으로 명시하세요. 엄격한 예산이 필요하면 요청 전 토큰 예약 또는 `max_tokens` 상한과 완료 후 실제 사용량 정산을 설계해야 합니다.

- **위치:** [리서치 §8-4 결론 5, 실습 한계](<../../../docs/research-multitenancy.md>)  
  **문제:** 목표 범위의 보안·격리 요구를 “측정으로 증명했다”는 서술이 실험 범위보다 강합니다.  
  **근거:** 실습 문서에서 egress 차단, 서비스 인증, 저장소·모델 격리, 메모리 격리는 미시험으로 적혀 있습니다.  
  **제안:** RBAC·ingress NetworkPolicy·Pod Security와 prefix-cache 타이밍 신호 등 **실제로 확인한 항목만** 사례로 제시하고, 나머지는 설계 또는 후속 과제로 표시하세요.

## 4. 다음 시험 우선순위

목표 범위(GPUaaS/LLMaaS) 전체와 현재 결론을 함께 고려하면 다음 순서를 권합니다.

1. **게이트웨이 PoC:** API 키 검증부터 테넌트 ID·우선순위·`cache_salt` 주입, 사용량 예약·정산까지 이어지는 흐름은 아직 실험하지 않았고 LLMaaS·과금 요구와 직접 맞닿아 있습니다. 테넌트가 우선순위를 위조하지 못하는지, 스트림·중복 청구·초과 요청·공정성도 함께 확인하세요.
2. **sleep mode 확장:** “보장형” 등급의 근거를 만드는 시험입니다. 드레인, 동시 wake 차단, 큰 모델, 3개 이상 테넌트, Kubernetes 전환과 대기시간을 검증해야 합니다.
3. **HAMi-core:** 공유 GPU의 메모리·컴퓨트 제한이 실제로 작동한다면 결론을 바꿀 수 있습니다. 다만 목표 범위 전체 기준으로는 인증·공정 큐·과금까지 다루지 않으므로 앞의 두 시험보다 뒤에 두겠습니다. **GPUaaS의 공유 GPU 격리를 우선 목표로 삼는다면 HAMi-core를 1순위로 올릴 수 있습니다.**

외부 문서 링크는 이번 리뷰에서 다시 열지 않았습니다. 위 평가는 지정된 문서와 로컬 원본 로그·스크립트에 한정합니다.
